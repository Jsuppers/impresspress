### Per-tier order views (#80, `e79d733`)

The last review finding, and the largest change. One `PurchaseView` served
buyer, seller and admin, so the buyer's own order list — and `list_my_purchases`,
the WebMCP tool built on it — published `platform_fee_cents`, the seller's Stripe
account, the provider handles and the reconciliation diagnostics.

Now three types: `BuyerOrderView` (drops 20 columns), `SellerOrderView` (drops
11), and `PurchaseView` unchanged as the admin projection. The split is by
**type**, not a runtime filter, because the type is what `/openapi.json` and the
manifest publish. That forced `handle_get` apart — it served both the buyer and
admin detail routes, which cannot both be right once they declare different
outputs — so `AdminRoute::GetPurchase` now dispatches to `handle_get_admin`.

Verified against the regenerated snapshot per tier: **every difference is a
removal; nothing is published anywhere it was not before.** The SDK got the same
split (`BuyerOrder` / `SellerOrder` / `Purchase`), `tsc --noEmit` clean.

Two judgement calls, both toward not changing existing behaviour, both open to
revision: the buyer keeps disputes on their detail (the SSR page already shows
them, and that endpoint is not an agent tool), and keeps `provider_status` on
refunds ("did my money come back" is what the endpoint answers; it is a state,
not a handle).

### Verified in a real browser

Chrome 146 here has **no WebMCP** — neither `navigator.modelContext` nor
`document.modelContext` exists. Testing used the same minimal `registerTool`
polyfill as the CI spec, with the site's real `webmcp.js` re-executed into it;
everything below that line is genuine. (The site's CSP blocks `eval`, so the

- Admin: 11 tools, every one with an object `outputSchema` — including
  `get_site_settings`, which had none before #81's fix.
- `list_my_purchases` after the tier split: 24 fields, zero platform/provider
  columns (it was 44 keys including `stripe_account_id` before).
- Live checks of the fixes against a seeded row with every platform column
  deliberately populated: all pass. e2e spec 8/8.

### A storefront at `/`, and what that corrected

`http://127.0.0.1:8095/` now serves a real shop: four products from the catalog,
each with a live configurator. This needed **no new code** —
`WAFER_RUN_SHARED__HAS_LANDING_PAGE=true` plus one `index.html` in
`data/storage/wafer-run/web/site/`. The page is kept at
`examples/landing-storefront/index.html`.

Getting there turned up things the examples had been hiding, because their suite
runs against a mock on `:4179` and they had **never met a real server**:

- Seeding `boutique-store`'s fixture through the real admin API works and prices
  identically to its own expectation (NZD 519.00, conditional rows and all).
- **CORS blocks the storefront widget's entire purpose by default.**
  `WAFER_RUN_SHARED__CORS_ALLOWED_ORIGINS` is empty, so the cross-origin embed
  the widget exists for fails silently. Serving the page from impresspress
  itself sidesteps it.
- **The widget takes a product id; every example passes a slug.**
  `product-id="archive-jacket"` resolves against the mock and 404s against a
  real server.
- **There is no cart anywhere** — `cart` appears in the products block only as
  an admin-page icon. Checkout is one offer plus quantity plus inputs.
- **There is no search** beyond `page` / `page_size`.

## 5. Traps worth not rediscovering

- **`pkill -f impresspress`** matches the shell running a script whose *path*
  contains "impresspress" and kills it (exit 144). Use a pid file.
- **A fresh worktree cannot build the `impresspress` crate** — the build script
  needs the gitignored `crates/impresspress-web/pkg/*.wasm`. `cp -r` it from a
  worktree that has one.
- **apport's excepthook** swamps Python tracebacks with unrelated PNG/ICO
  output. Redirect to a file and grep.
- Local runs build against a scratchpad `[patch]` of wafer-run; **CI on the
  pinned rev is canonical** for the snapshot gate.
- `wasm_bindgen_test`s in `impresspress-cloudflare` are typechecked by
  `cargo check --target wasm32 --tests` but **executed by nothing** — CI has no
  wasm test job for that crate. Worth adding.

## 6. Still open

**Human, gating the submission:** the demo video (<3 min), an agent-driven
browse → price → checkout in a real WebMCP browser (the one thing no test
covers), and the write-up naming both repos.

**Engineering, not gating:** products' 22 offer sites (recursive `Condition`,
needs the `$defs` hoist in wafer-run); the `$defs` hoist itself;
**impresspress#78** — shared `WAFER_RUN_SHARED__*` variables have no read path
on Workers, so config edits never reach the running Worker. #78 blocks Stripe
configuration on the live demo and is the prerequisite for anything
config-driven.

**From the reviews, not fixed** — the long tail was triaged and left. The ones
worth a second look: `page as u32` truncation in #74 and #80 (a large `?page`
wraps onto a real page instead of an empty one); non-finite `f32` serializing as
`null` against non-nullable `number` schemas (#79, #80); three cross-repo
workarounds flagged against the workspace's root-cause rule (`files` contracts
mirroring wafer-run wire types, `auth_rank` as a third copy of the `AuthLevel`
ordering, `view_schema` copying wafer-block's private `self_contained_schema`);
and `list_audit_log` publishing `ip_address` into a page agent's context.

**#73** (`feat/pixel-art-brand`, not this effort) was reviewed and has real
findings: flipping the `LOGO_URL` default to blank strips branding from every
userportal account card, because `account_card_page` never got the text fallback
the other templates did; and the deleted `/b/static/impresspress-logo-long-*`
route 404s for any deployment that persisted the old default.
